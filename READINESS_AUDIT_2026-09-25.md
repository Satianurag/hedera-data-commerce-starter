# Neuron × Scaffold-HBAR: pre-implementation readiness audit

**Historical snapshot:** This audit records evidence gathered before the candidate existed. The current public template, compatibility matrix, live testnet results and remaining gates are tracked in [AGENTS.md](AGENTS.md), the [26 September evidence](docs/testnet-evidence-2026-09-26.md) and the [source ledger](docs/source-ledger-2026-09-26.md). Statements below such as “no candidate code” describe the earlier audit checkpoint.

**Checked:** 25 September 2026. **Scope:** upstream tests, read-only network verification, Neuron reference-demo testnet HCS writes, real testnet HBAR transfers between user-controlled accounts, deployed testnet EVM contract transactions, and live requests to external Neuron sellers. No product code or mainnet writes were part of this historical audit. The supplied research report and older config files are evidence/test data, not implementation instructions. At this audit checkpoint, the workspace had no application files or commits, so there was no candidate template to install, boot, or test end to end.

## Decision

**Go for a staged, explicitly experimental testnet-first integration plan; no-go for claiming a ready Neuron customer-commerce template or mainnet support.** Upstream protocol tests passed; a fresh signed Neuron heartbeat and a reference buyer–seller exchange ran on real testnet HCS. A separate HBAR transfer between two owned accounts and an ERC20 escrow lifecycle on deployed testnet contracts also succeeded. A disposable buyer made real service requests to **all nine supplied external sellers** and, through verified public UDP tunnels, received **nonzero P2P data from every seller**. Independently verified scheduled transfers from our buyer's shared accounts paid **eight distinct sellers** in testnet HBAR; one seller's stream failed in two multi-seller sessions and did not invoice our buyer in its observed billing window, but streamed continuously for over three minutes in one- and two-seller control runs. Raw Mode-S/ADS-B frames from two sellers were independently decoded from the buyer's binary ingress logs, but the WebSocket wrapper corrupted invalid UTF-8 bytes and the supplied NodeBuilder JSON-lines flow did not parse the stream. The payment code did not validate delivery or invoice before signing. Public Agent Card discovery, an installable TypeScript SDK, a working application-level decoder, a safe delivery-to-payment binding, Hedera-native escrow, and a mainnet path remain unproven.

The bounty closes **4 October 2026 at 11:59 p.m. ET**. Its [full brief](https://hedera.com/blog/scaffold-hbar-template-bounty/) asks for a public MIT monorepo with separate frontend/contracts packages, Next.js plus Hardhat or Foundry, npm or Yarn workspaces, Node ≥20.18.3, a valid `template.json`, README and AGENTS.md, clean scaffold/install/lint/build/boot, and a verifiable **testnet transaction from the submission**. The prior Neuron transaction is useful background evidence but cannot validate a template that does not yet exist.

## Follow-up with the supplied older buyer files

The attached `buyer-env` has the field names documented by the [legacy Neuron Go Hedera SDK](https://github.com/NeuronInnovations/neuron-go-hedera-sdk/blob/44cec0a/README.md), not the current spec-first TypeScript configuration. Its testnet RPC/Mirror URLs and old contract address confirm its intended network. The locally stored ECDSA private key derives the file's configured EVM identity; the corresponding testnet account has that EVM address and was funded. The newly supplied public key and EVM address match **another** funded ECDSA testnet account. The same numeric account IDs exist independently on mainnet with **different** EVM addresses/keys and zero balances. Network-specific ID, key, and address checks must therefore fail closed before signing.

The older file lists **nine seller compressed public keys**. All nine match DER-formatted public keys in the [public legacy device registry](https://explorer.neuron.world/api/v1/device/wip-all). On 25 September 2026 all nine seller stdout topics had recent `NeuronHeartBeat` messages, with versions ranging across the 0.52.89–0.52.106 family. For all nine, the **latest** message payer matched the registry's Hedera account, and that account's on-chain ECDSA public key matched the registered key. All nine topics have no `submit_key` and are therefore open to other payers; a reader must filter and verify every message, not trust the topic alone. All nine heartbeats reported `natReachability: false` while listing two or three connected peers, so a customer app must test the actual relay/connection route rather than assume direct inbound connectivity. This is strong evidence of current activity by those registered accounts; it does not prove physical sensor truth, an available buyer data stream, or compatibility with the signed spec-first browser profile. The attached location file has 12 entries: all nine listed sellers are covered, with three extra entries. The nine shared coordinates differed from the latest public heartbeat locations by at most **0.11 km** at check time; no coordinates or names are reproduced here.

The old config's contract address resolves to **testnet contract `0.0.3699889`**, created in 2024 and not deleted; the same EVM address returned 404 on mainnet. A fresh read-only `eth_call` through HashIO using the public legacy Go binding's ABI returned `getPeerArraySize() = 1215`, and `hederaAddressToPeer(address)` returned `available: true` plus the expected stdout/stdin/stderr topic IDs for seller 2 (`0.0.6340259`), seller 4 (`0.0.4318411`), and our disposable buyer (`0.0.10712332`). This independently validates the **legacy peer-directory role and ABI compatibility for those entries** on testnet. The binding exposes registration and peer/topic getters, but no price getter; the registry's advertised service `fee` is not thereby validated as an on-chain settlement price. Its compatibility with current spec-first Agent Cards and commerce remains unestablished.

Mainnet lookup of all nine testnet seller topic numbers found **two numeric collisions**: `0.0.5146586` and `0.0.5146701` are also existing mainnet topics, but their mainnet metadata has submit keys and their latest messages have a payer unrelated to the testnet registered sellers. The other seven topic lookups returned 404. This is a concrete failure case for any app that switches a Mirror Node base URL while reusing a saved topic ID; topic existence alone is insufficient without expected network, payer/key, schema, and deployment identity checks.

Using only the older file's key locally (never printed or copied into this repo), the current spec-first Go reference `hcs-heartbeat-test` created [testnet topic `0.0.10709339`](https://testnet.mirrornode.hedera.com/api/v1/topics/0.0.10709339/messages?limit=1) and published a signed `heartbeat` v1.0.0. Independent Mirror reads showed sequence 1 and a matching [`CONSENSUSSUBMITMESSAGE` / `SUCCESS` transaction](https://testnet.mirrornode.hedera.com/api/v1/transactions/0.0.8315145-1790314210-234568085). The demo initially printed `Confirmed: false` even though its later Mirror verification succeeded; the eventual application must distinguish pending, consensus success, and Mirror indexing rather than exposing that boolean as final status.

The same test account then completed the reference buyer–seller demo. Runtime created **nine** HCS topics, though the [guide](https://github.com/NeuronInnovations/neuron-specs/blob/13ab01d70ac42531065094a52cd595ef7b6d3223/docs/getting-started/demos/7-hedera-full-commerce.md) still describes six. ## Compatibility findings that change the design

1. **Scaffold network selection is not an application network guard.** CLI 0.4.0 parses `--network testnet|mainnet`, but its source does not use that choice to wire runtime network configuration. The template must bind SDK, Mirror Node, topic IDs, account IDs, wallet chain, evidence URLs, and fees to one explicit network. The CLI can also fall back to permissive manifest defaults when capabilities cannot be fetched; `--ci` then selects defaults that may differ from the intended project. See [capability handling](https://github.com/hedera-dev/create-scaffold-hbar/blob/5732f5efb63e1522658f236d329d09250136bd09/src/utils/template-capabilities.ts), [manifest schema](https://github.com/hedera-dev/create-scaffold-hbar/blob/5732f5efb63e1522658f236d329d09250136bd09/src/types.ts), and [copy logic](https://github.com/hedera-dev/create-scaffold-hbar/blob/5732f5efb63e1522658f236d329d09250136bd09/src/tasks/copy-template-files.ts).
2. **The Scaffold baseline is not currently a clean proof of the bounty gate.** It pins Next 15, React 19, Hiero/Hashgraph JS SDK 2.x, Hardhat 2, and Yarn 3.2.3; this host has Node 26, npm 11, and Yarn classic 1.22. The explicit Node 20.18.3 official baseline run found contract type errors and a failed Next build, while transitive package engines already exceed the bounty's stated Node floor. A separate external template built and booted successfully with Node 22/Yarn 3 but its same locked dependency graph failed a Node 20.18.3 build on `@walletconnect/modal` ESM loading. Upstream Neuron tests independently passed at Node 20.18.3. The eventual template needs its **own pinned lockfile** and clean Node 20.18.3 plus Node 22, npm and any claimed Yarn 3 gates. [Scaffold baseline](https://github.com/hedera-dev/scaffold-hbar/tree/5eb46ef3eaa8fae7613669fa6edcde4357ab7670).
3. **Two Neuron generations are being conflated.** The active testnet `NeuronHeartBeat` JSON looks like an older operational format. It is not the signed Spec 004 envelope, Spec 005 identity/liveness proof, or full Agent Card workflow described by the current spec-first repository. A generic decoder can display it, but must label its authentication level accurately. [Neuron spec repository](https://github.com/NeuronInnovations/neuron-specs/tree/13ab01d70ac42531065094a52cd595ef7b6d3223).
4. **Draft deployment claims remain draft.** The supplied Discord exports do contain the cited staff statements about edge/coordinator separation, Agent Cards, commerce choices, and privacy nodes. Their wording describes demos, architecture, or work “almost finished” / coming soon. Public deployed endpoints, registry addresses, and interoperable customer flow were not independently found; these claims cannot be treated as shipped features.

## Edge cases the eventual template must prove

- **HCS:** wrong network with empty-200 results; missing/deleted topic; custom topic fees; insufficient payer balance; duplicate/out-of-order/missing sequence; malformed base64/JSON; unknown schema/version. The **1,024/1,025/2,048-byte** live test confirmed chunking, exact reassembly, and relative-URL Mirror pagination. A separate live submit-key test confirmed unauthorized `INVALID_SIGNATURE` versus authorized `SUCCESS`; legacy seller topics remain open. The eventual app parser still needs these cases. [HCS](https://docs.hedera.com/native/consensus/submit-message), [Mirror API](https://docs.hedera.com/api-reference/topics/list-topic-messages-by-id).
- **Confirmation:** wallet/SDK returning a transaction ID is only submission. Require consensus receipt `SUCCESS`, then bounded Mirror polling and matching topic/transaction/sequence. Handle indexing lag, 404, 429, 5xx, timeouts, and provider outage without blindly resubmitting. [Receipts](https://docs.hedera.com/native/transactions/receipt), [Mirror architecture](https://docs.hedera.com/operators/mirror-node/architecture).
- **Trust/session:** forged or unsigned heartbeat, stale/replayed control message, mismatched EVM address/PeerID/Agent Card, key rotation, revoked seller, stale explorer entry, seller STOP failure, old stream in new session, direct connection failure, relay fallback, backpressure and delayed data. A fresh HCS heartbeat alone must not set “service available.”
- **Money:** distinguish native HBAR's 8 decimals from JSON-RPC's 18-decimal EVM value and each ERC20 token's own decimals; use integer units and explicit asset labels. The observed demo treated 18-decimal TestToken base units like 8-decimal HBAR tinybars. Test HTS association/KYC/freeze/decimals if token settlement is chosen. A created schedule does not establish successful execution of its inner transfer, and a scheduled transfer alone is not delivery-conditioned escrow. The live buyer-only refund probe failed `INVALID_SIGNATURE`, so cancellation must name the required signers and verify actual fund recovery. [Decimals](https://docs.hedera.com/evm/differences/hbar-decimals), [schedules](https://docs.hedera.com/learn/core-concepts/transactions/scheduled).
- **Listed price:** the legacy registry's `fee` values 1.0 and 0.5 did not map to different observed 0.1 HBAR shared-account debits for sellers 2 and 4. Its units and settlement relationship are unknown; require an explicit quote, asset, amount, duration and signed invoice before showing a buyer price or signing a schedule.
- **EVM provider:** reject implausible base fee/gas price combinations, set a valid Hedera fee strategy, bound receipt polling, recover from provider indexing lag, reconcile with Mirror Node, avoid duplicate approval/deposit when an RPC returns `null`, and test both supported RPC providers before relying on the adapter.
- **Scaffolding/security:** npm and claimed Yarn installs, Node 20 floor, manifest capability fallbacks, pruning/rewrite of unselected packages, zero-secret boot, browser/server signer separation, no `.env` or private key committed, and `NEXT_PUBLIC_*` never carrying a secret.
- **Command discovery:** the current scaffold root has `next:build`, `next:check-types`, and `hardhat:check-types`, but no root `build` or `typecheck` script. The candidate's README/CI must call real scripts or provide its own consistent root scripts; a copied checklist command is not a test result.
